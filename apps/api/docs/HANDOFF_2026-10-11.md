## 3. Root cause — `cloudflare.config.ts` hardcodes the target

`@vinext/cloudflare deploy` does **not** read `wrangler.staging.jsonc` /
`wrangler.d1.jsonc` (those are only for the `wrangler` CLI, e.g. D1 migrations).
The vinext build (via `@cloudflare/vite-plugin`) resolves its target from
`cloudflare.config.ts`, which hardcodes:

```ts
worker: defineWorker({
  name: "myrota",
  env: { DB: bindings.d1({ name: "myrota" }) },   // ← pilot/production Worker + DB
})
```

So **every** `build:vinext` + `@vinext/cloudflare deploy` targets the production
`myrota` Worker, regardless of any `--config` flag. The `@cloudflare/vite-plugin`
`PluginConfig` type exposes no `configPath`; the worker name is baked at build time.

**To deploy to staging:** temporarily set `cloudflare.config.ts` `worker.name` →
`"myrota-staging"` and `DB` → `bindings.d1({ name: "myrota-staging" })`, rebuild,
deploy, then revert (do not commit the staging edit). A dedicated
`cloudflare.staging.config.ts` + a `deploy:staging` npm script would make this
safe and repeatable — **recommended before the next staging deploy.**
